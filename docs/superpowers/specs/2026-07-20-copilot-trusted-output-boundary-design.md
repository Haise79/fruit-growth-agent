# Copilot Trusted Output Boundary Design

Date: 2026-07-20

## Goal

Ensure every persisted and returned copilot suggestion consists only of
deterministic server text, fresh SQL SKU facts, and explicitly referenced,
approved knowledge. Model-authored `suggestion_text` and `risk_tip` never cross
the persistence boundary.

## Validated design

The existing `CopilotService` remains the orchestration boundary. After loading
fresh tenant-scoped SQL evidence, it validates complete typed claims against the
selected SKU. `shipping_eta` is a required field whose value may be null; it is
always normalized and compared to SQL, including null/value mismatches.

Suggestions are assembled in model order after de-duplicating by SKU code. The
model may select and rank distinct verified SKUs, but it cannot supply displayed
text. A deterministic renderer chooses a template from the controlled
`stage`/`intent` classification and reads only `ProductSKURead` fields:

- delivery: `shipping_eta` and `sales_regions`;
- storage: SKU ripeness/specification plus approved storage/FAQ knowledge;
- gift: specification, net weight, origin, and taste;
- product information/recommendation: canonical price, inventory, origin,
  net weight, variety, taste, and specification as relevant.

Only knowledge IDs included in the model's reference list and already present
in the service's approved/current semantic evidence may contribute content.
The renderer labels this as an approved knowledge note. No other model text is
concatenated.

`risk_tip` is generated by a deterministic policy from controlled case state.
For persisted suggestion-ready cases it maps risk and intent to fixed server
copy. Handoff/conflict reasons remain on the case and produce no suggestions.

## Security invariants

1. Model `suggestion_text` and `risk_tip` are discarded.
2. Complete claims, including a present `shipping_eta`, must equal fresh SQL.
3. A missing claim field, SQL value/claim null mismatch, or contradictory claim
   causes handoff with no suggestion persistence.
4. Rendered output contains no arbitrary model prose.
5. Approved knowledge is included only through an ID intersection with the
   exact evidence supplied by the server.
6. Duplicate model drafts for the same SKU produce at most one card.

## Tests

Integration tests cover hostile model text containing a false price and
`wxid`, required/null shipping ETA behavior, delivery/storage/gift/product
templates, approved knowledge inclusion, unapproved knowledge exclusion,
distinct-SKU cards, and duplicate-SKU suppression. Schema tests cover omitted
`shipping_eta`.
